When something is wrong

Tome collects nothing and phones home never, so the only thing that knows what happened on your machine is your machine. Two commands get it to say so.

Start here

$ tome debug check

It reports and never repairs — a check that fixes things cannot be run twice to see whether the fix worked. It verifies that the library is writable, the database opens, every source configuration parses, the index opens, and that the index and the database agree about how many pages each source has. Each failure line names the command that fixes it, and it exits non-zero, so tome debug check && tome pull --all does the right thing.

The last of those checks is the one worth having. An interrupted pull leaves the database ahead of the index; search then quietly misses pages that are sitting on your disk, and nothing anywhere says so.

no symptom the only failure here that you would never notice on your own

An empty library is reported as healthy. A first run is not a fault.

Search is missing things, or will not open

$ tome debug rebuild-index

Discards the index and rebuilds it from the pages already on your disk. No network. Your configurations, your database and your fetched content are untouched: the index is derived, which is exactly why it lives in the cache directory.

5–21 s to rebuild 100 000 pages, against about seven hours to re-crawl them (measured)

If Tome tells you the index was built for an older version, this is the command it means. It used to say tome pull --all, which also works and also re-crawls every site you have.

A source stopped producing pages

Sites get redesigned, and a scraper tuned to the old markup keeps parsing and stops finding anything. The symptom is a pull that succeeds and stores far fewer pages than last time. 

$ tome pull rust-std
rust-std: 3 pages in 2.1s

A pull always says what it missed — pages that failed, assets that could not be localized, and whether it stopped at the page cap — because a crawl that reports success while having silently skipped two hundred pages is worse than one that says what it missed. If the numbers look wrong, the configuration is the place to look: ~/Library/Application Support/Tome/sources/.

A pull may also report that pages were removed. That happens only when the crawl finished cleanly, hit no page cap, saw no ambiguous errors, and found at least one page — otherwise Tome deletes nothing, because a crawl that stopped early did not look at the pages it did not see.

macOS refuses to open the app

$ xattr -dr com.apple.quarantine /Applications/Tome.app

Expected, once per install — and run it before you open Tome. Opening it first gets you “Apple could not verify Tome is free of malware”, whose default, highlighted button is Move to Trash. The command prevents that dialog; it cannot dismiss one already on screen. If the app has already been trashed, brew reinstall --cask tome and run the command first.

macOS 15 removed the Control-click then Open bypass, so this is the way rather than a shortcut for it. Homebrew no longer offers --no-quarantine either.

Reporting a bug

$ tome debug report

Prints something you can paste into an issue: version, OS, where the library lives, which sources you have with page counts and dates, the check findings, and the tail of the log.

redacted no page paths, no search queries, no note text, and $HOME rewritten to ~

Read it before you send it. It is designed to be safe to publish — which pages you have read is not in it, and a test types a distinctive search query and asserts it appears nowhere — but it is your machine and your call.

The logs it reads from are at ~/Library/Application Support/Tome/logs/, one file per day, kept for seven. They never leave your machine on their own.

Getting rid of it

$ tome config forget-token
$ brew uninstall --zap tome

In that order. The zap removes the library, the caches and the app; it cannot remove the API token, because that is in the Keychain and the Keychain is not a file. If you never ran tome serve there is no token and the first command says so.

Things that are not bugs

What you see Why
An image says “unavailable offline” That asset could not be localized during the crawl. The page still renders; re-pull to try again.
A page Tome refuses to fetch The site’s robots.txt disallows it. Tome obeys it by default and there is no override for registry sources.
The search index vanishing after an upgrade The index schema changed. Rebuild it — the content is untouched and the rebuild needs no network.
A global shortcut that does nothing macOS reserves some combinations, and registering one of those succeeds and then never fires. Tome refuses the ones it knows about; pick another.
Sync doing nothing There is no sync. It is designed and deferred, not broken.
