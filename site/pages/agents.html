Agent access

Your coding agent reads the documentation you actually have, for the versions you actually pinned — not what it remembers, and not what it can reach over the network.

Claude Code

Install the plugin. It bundles the MCP server, so there is nothing else to configure.

> /plugin marketplace add alexnodeland/tome
> /plugin install tome

Check it took:

> /tome:list

If the tools do not appear, tome is not on the PATH Claude Code sees. Run which tome in the same shell you launch it from.

silent failure an MCP server that cannot start does not announce itself — its tools are simply absent

Or wire it up by hand

Any MCP client that spawns processes:

{ "mcpServers": { "tome": { "command": "tome", "args": ["mcp"] } } }

The tools

Tool Does
tome_search Search every source, or one via scope. @name searches declared symbols only.
tome_get_page Read a page as markdown. section reads one heading's subtree.
tome_list_sources What is in the library, with page counts.
tome_get_toc One source's pages, in navigation order.
tome_lookup_symbol Pages that declare a symbol, not every page mentioning it.

All five are read-only, and that is a security boundary rather than a simplification. The documentation Tome ingests is untrusted text that agents read; a prompt injection in a scraped page must not be able to reach a write. Anything that changes your library is a command you type.

no writes when a write-capable tool exists it will be opt-in and off by default

Long pages

A page result is capped and cut at a block boundary — never mid-sentence, never through a code fence — and the truncation notice lists the page's sections so the next call needs no guessing. Pass section with a heading anchor to read just that part.

48 KiB ≈ 12k tokens · an oversized result is not a transport error: the client diverts it to a file and the model gets a filename instead of the page

Slash commands

The plugin adds five, for the things you do rather than the things the agent does.

/tome:add <url> Detect, configure, pull
/tome:search <query> Search, then open the best result and answer from it
/tome:list What is in the library
/tome:pull <id> Fetch or update
/tome:remove <id> Remove a source, after confirming

/tome:search opens the best result rather than answering from titles. A title match is not an answer, and opening a local page costs nothing.

158 µs P95 search · reading the page is the cheap part

Protocol notes

The server speaks the handshake-based MCP revision (2025-11-25 and earlier), deliberately. The current specification revision replaced that handshake with per-request versioning, but the shipping client still opens with initialize and has no way forward from a server that only speaks the new one.

tested, not assumed a hello-world server was built and connected to the real client before any of this was designed · SPIKE-008

Nothing but protocol messages is ever written to stdout — a stray line corrupts the stream — and the server exits cleanly when its client goes away, leaving no orphan process. Both are pinned by tests that run the real binary.

The HTTP API

If your tooling cannot spawn a process, there is a local REST API instead. It is off unless you run tome serve, and every request needs a bearer token including on loopback. 

$ tome serve
$ curl -H "Authorization: Bearer $(tome status --show-token)" \
       http://127.0.0.1:7431/api/v1/search?q=vec

A web page you visit cannot read it. No CORS headers are emitted by default, and a request carrying an Origin that is not on the allowlist is refused outright — which stops it having effects, not just being read.

verified in a browser a hostile page could not read the API even holding a valid token, and its opaque no-cors request was refused server-side
